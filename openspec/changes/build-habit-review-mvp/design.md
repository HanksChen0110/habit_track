## Context

本项目要实现一个单人、本地优先的习惯执行记录与每周复盘 Web/PWA。此前的设计草案以连续天数和长期仪表盘为中心；本次变更以已确认方案为准：每天只记录完成量，每周用整体执行率和日期规律帮助用户调整下一周安排。

项目当前没有应用源码或后端。数据只留在当前浏览器，手机与桌面是同一产品的两种响应式布局，不自动同步。首轮验证对象为作者和至少两位朋友，持续 21 天。

## Goals / Non-Goals

**Goals:**

- 用客户端领域规则确保补记、归档和新增习惯不会追溯改写既往统计。
- 让用户在手机或桌面上都能完成记录、周报和管理；手机优先快速记录，桌面突出周报入口。
- 用可校验的本地 JSON 数据模型支持刷新后恢复、导出、导入替换和失败保护。
- 用纯计算函数生成周报，便于对日期边界、部分完成量和历史口径做自动化测试。

**Non-Goals:**

- 不提供账号、服务器、云同步、跨设备数据共享或协作。
- 不提供提醒、连续天数、长期热力图、备注、原因推断、分享或商业化功能。
- 不支持每周目标、非每日频率、目标版本历史或直接修改已有记录习惯的每日目标。

## Decisions

### 1. 单页客户端 PWA，不引入后端

应用使用纯浏览器端的响应式单页架构。所有日常交互、统计和数据管理在设备本地完成；应用不得依赖账号、API 或第三方服务。

选择理由：当前验证只需要单设备个人使用，本地架构将隐私、部署和运维成本降到最低。相比“手机记录、桌面复盘并自动同步”，它牺牲跨设备连续性，换取最小可验证闭环。

替代方案：

- 账号和云同步：能支持双设备同数据，但会引入身份、服务端、隐私和恢复责任，不符合 MVP。
- 手动导入导出作为日常同步：保留无账号，但操作成本过高，不能作为主路径。

### 2. 版本化 Store 与不可变历史口径

浏览器维护一个版本化的 Store，并将整个 Store 以 JSON 保存在一个固定的浏览器本地存储键中。习惯以本地自然日 `createdOn` 和 `archivedOn` 定义其有效区间；完成记录以 `(habitId, date)` 作为唯一键。每次更新使用替换式写入：同日同习惯更新同一条记录，计数归零时删除该条记录。

按日期计算 `activeOn(date)`：创建日计入，归档日计入，归档次日失效。统计必须使用该日期当时有效的习惯和目标，而不能使用今天的活跃习惯集合。每日目标只可在**创建当天且尚无任何完成记录**时修改；从创建次日起或产生任意完成记录后即锁定。改目标通过归档旧习惯并新建习惯实现。

选择理由：仅以“已有记录”锁定目标仍会让一个已创建多日、但尚未记录的习惯在修改目标后重算过去的计划量。创建当日以外锁定目标，用最少的数据结构保证历史可信，不需要目标版本历史。

Store 的规范结构如下；`id` 为非空且在数组内唯一的字符串，所有日期均为有效的本地 `YYYY-MM-DD` 日期：

```text
Store
  version: 1
  habits: Habit[]
  completions: Completion[]

Habit
  id: string
  name: trimmed non-empty string
  targetPerDay: positive integer
  createdOn: YYYY-MM-DD
  archivedOn: YYYY-MM-DD | null

Completion
  habitId: existing Habit.id
  date: YYYY-MM-DD
  count: integer in 1..targetPerDay
```

每次命令的提交顺序固定为：基于已持久化 Store 生成候选 Store → 完整校验候选 Store → 写入本地存储 → 写入成功后再更新界面状态并提示成功。若写入失败，界面回到持久化前状态；同一浏览器的其他标签页写入该存储键时，当前标签页必须重新读取并提示数据已更新，不能继续基于过期快照静默覆盖。

### 3. 周报由纯函数按“已过去日期”计算

周固定为周一至周日。已结束周统计完整七天；当前周仅统计周一至今天，以免未来日期被误记为未完成。单个习惯某日的实际完成量为 `min(count, targetPerDay)`；整体执行率为有效习惯实际完成量之和除以计划完成量之和。

周报的输入是 Store 和周起始日，输出是整体执行率、逐日执行率、最佳/最差日期以及**紧邻的上一个已结束自然周**的整体执行率。只有紧邻周存在计划完成量时才显示环比；不得跳过空周寻找更早一周。无计划完成量的日期显示“无计划”，不参与日期高低比较；可比较日期不足两天时不显示“最佳/最差日期”。计算层不推断用户未完成的原因。

### 4. 本地数据的原子导入与显式失败状态

Store 使用浏览器本地持久化，导出为可读 JSON。导入先完整解析和校验，再显示替换数量，只有用户确认后才一次性替换 Store。任何解析、校验或写入失败都保留旧 Store 与旧 UI 状态，并给出明确错误。

选择理由：本地产品的长期价值来自记录积累；虽然不能避免用户清除浏览器数据，但至少不因损坏文件或半成品写入静默毁掉已有记录。

### 5. 两端完整闭环，按信息层级而非功能拆分

两端都包含“今天”“本周”“管理”。手机默认进入今天页，使用单列习惯行和大触控区；桌面也默认进入今天页，在同屏侧栏显示本周摘要和完整周报入口。任何端都不能把每日记录、周报或管理隐藏为不可达功能。

#### 低保真线框：手机端

```text
┌──────────────────────────┐
│ 周五，7 月 24 日          │
│ 今日完成量 2 / 4          │
├──────────────────────────┤
│ 阅读              − 1/1 + │
│ 运动              − 1/1 + │
│ 英语              − 0/2 + │
├──────────────────────────┤
│ [查看本周复盘]            │
├──────────────────────────┤
│ 今天       本周       管理 │
└──────────────────────────┘
```

#### 低保真线框：桌面端

```text
┌────────────────────────────────────────────────────┐
│ 今天                                                 │
│ 周五，7 月 24 日                  ┌──────────────┐ │
│ 今日完成量 2 / 4                  │ 本周 72%     │ │
│ ─────────────────                 │ 较上周 +8pp │ │
│ 阅读                 − 1/1 +      │ 最低：周六   │ │
│ 运动                 − 1/1 +      │ [进入周报]  │ │
│ 英语                 − 0/2 +      └──────────────┘ │
│ [最近 7 天：修正漏记]                                 │
└────────────────────────────────────────────────────┘
```

线框只定义任务层级和内容，不预设色彩、字体或视觉风格。完成状态、部分完成、空状态和错误状态必须同时有文字或数值，不能只靠颜色。

### 6. 交互状态、层级与可访问性

所有界面先呈现用户此刻最需要完成的任务：今天页依次为日期与今日完成量、习惯记录列表、周报入口；周报页依次为周范围与“进行中”状态、整体执行率、逐日执行率、日期规律和环比；管理页依次为习惯管理、导出、导入。平板宽度（321–1023 CSS 像素）沿用手机的单列层级，不压缩为桌面双栏。

| 功能 | 空状态 | 成功/部分状态 | 失败状态 |
| --- | --- | --- | --- |
| 今天记录 | 无活跃习惯时显示“先创建一个每日习惯”及创建入口 | 显示“今日完成量 实际/计划”；部分完成保留实际数值 | 保存失败时保留旧值并显示“未保存，请重试” |
| 周报 | 范围内无计划量时显示“本周暂无可复盘的数据” | 当前周明确显示“截至今天，进行中”；无计划日标为“无计划” | 统计无法读取 Store 时显示恢复入口，不显示猜测数值 |
| 导入 | 未选择文件时仅提供选择入口 | 校验通过后显示替换数量，确认后提示已替换 | 解析、校验或写入失败时说明原因，旧数据和页面保持不变 |

加减控件必须是带可见文字或无障碍名称的按钮（例如“阅读，增加一次”），可用键盘操作并有清晰焦点状态；保存/导入结果使用可被辅助技术读出的状态提示。正文与状态文本满足至少 4.5:1 对比度，触控目标不小于 44 CSS 像素。视觉实现保持克制的应用界面：以记录列表和周报内容为主，不用装饰性卡片网格或仅靠阴影区分信息层级。

## Risks / Trade-offs

- [不同设备数据互不相通] → 首版明确声明单设备使用；导出/导入只用于备份和迁移，不作为日常同步。
- [浏览器清除站点数据] → 提供完整 JSON 导出与导入；在产品文案中不把本地存储描述为永久备份。
- [同一浏览器多标签页相互覆盖] → 监听本地存储变更并重新读取最新 Store；界面只在本标签写入成功后确认保存。
- [当前周被错误评价] → 仅将截至今天的日期计入当前周分母，并显式标记“进行中”。
- [新增、归档或改目标后历史变动] → 使用按日期有效的习惯集合；每日目标仅可在创建当日、且无记录时修改。
- [小屏操作密度过高] → 手机使用单列、至少 44 CSS 像素的加减触控区和底部导航；桌面才使用并列周摘要。
- [PWA 缓存旧静态资源] → 应用版本更新时刷新应用壳资源；用户数据与静态资源缓存分开管理。

## Migration Plan

本次是新应用，没有历史生产数据迁移。

1. 首次运行创建空的 `Store(version: 1)`。
2. 后续版本若改变 Store 结构，必须先增加显式迁移或拒绝导入未知版本；不得静默重置用户数据。
3. 发布前验证新浏览器、刷新页面、导出后导入三个恢复路径。
4. 出现导入或写入错误时不替换旧 Store，用户可导出已有可读数据后恢复。

## Open Questions

无。技术框架可在实现任务开始时选用依赖少、支持 TypeScript、静态部署和自动化测试的前端工具链，但不得改变本设计中的产品与数据边界。
