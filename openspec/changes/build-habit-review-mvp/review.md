# MVP 规格多视角评审记录

评审日期：2026-07-24
评审对象：`build-habit-review-mvp`

## 结论

规格可进入实现准备阶段。评审没有扩大产品边界，已直接修正会导致历史数据失真、统计解释不一致、导入覆盖和双端交互不可靠的问题。实现前仍需按 `tasks.md` 选择前端工具链并完成测试环境初始化。

## CEO 视角：产品与验证

| 发现 | 风险 | 已纳入的处理 |
| --- | --- | --- |
| “每周复盘带来调整”原先只有口头验证标准 | 21 天试用只能证明用户看过周报，不能证明它改变了安排 | 任务 6.5 改为在产品外的试用记录中写下并在下次复盘核验一项可观察调整；不向产品加入备注功能 |
| 当前周过早显示最佳/最差日期 | 周一或只有一个有计划日就会制造虚假的“规律” | 仅在至少两个有计划日期时显示日期规律；无计划日不参与比较，当前周标注进行中 |
| 单设备本地边界容易被误解为双端连续使用 | 用户可能在手机记录、桌面复盘时误以为数据会自动出现 | 维持单设备边界，导入/导出只作为备份与迁移，文案不得暗示自动同步 |

## 工程视角：数据、统计与验证

| 发现 | 风险 | 已纳入的处理 |
| --- | --- | --- |
| 无完成记录的老习惯仍能修改每日目标 | 会重算创建日至今的计划量，破坏历史周报 | 每日目标仅可在创建当天且无记录时修改；之后通过归档旧习惯并新建处理 |
| “上一个有数据周”与“紧邻上一周”混用 | 比较对象不可预测，用户无法解释环比 | 固定为仅比较紧邻的上一个已结束自然周；相邻周无计划量则不比较 |
| 最近 7 天未定义边界 | 不同实现可能得到 7 或 8 天窗口 | 固定为今天减 6 天至今天，含首尾 |
| Store 结构和写入顺序不足够具体 | 导入、回滚、跨标签页会出现实现分歧或静默覆盖 | 补充规范 Store、候选校验→持久化→界面提交顺序及同浏览器标签页刷新规则 |
| 测试任务漏掉上述边界 | 代码看似可用但会在补记、导入或周报边界回归 | 已补齐领域、持久化、端到端测试任务 |

## 设计视角：双端体验与可访问性

| 发现 | 风险 | 已纳入的处理 |
| --- | --- | --- |
| 今天页的 `2 / 3` 可被理解为“达标习惯数”，但周报使用完成量 | 每日和周报的分子分母不一致 | 统一为“实际完成量 / 计划完成量”，并更新手机、桌面低保真线框 |
| 平板布局没有定义 | 实现时容易在中间宽度压缩双栏导致控件不可用 | 321–1023 CSS 像素固定使用单列记录层级 |
| 空、部分、错误、导入状态未形成可验收要求 | 只会得到正常路径界面 | 在设计文档加入状态矩阵，并补充相应任务 |
| 键盘、辅助技术和焦点状态仅泛泛提及 | 核心加减、保存结果对部分用户不可用 | 明确可聚焦控件、可读名称、状态提示、对比度和 44px 触控目标 |

## 明确不在本次调整中处理

- 自动跨设备同步：会引入账号或同步冲突处理，违背本地 MVP 边界。
- 产品内“下周调整”备注：会改变已确认的无备注数据模型；先用试用协议验证是否值得做。
- 提醒、连续天数、长期图表与原因推断：不服务于本次“低负担记录 + 周复盘”验证。
- 最终视觉品牌、字体和配色：当前阶段只固定信息层级与可访问性约束；实施前可单独进行视觉设计。

## 实施前检查清单

1. 以 `design.md` 和四份能力规格为行为来源，不使用已替代的历史仪表盘文档。
2. 先完成 `tasks.md` 第 1 节的工具链和测试入口，再实现领域规则。
3. 实现时优先覆盖目标锁定、日期窗口、相邻周比较、导入回滚和写入失败。
4. 应用完成后运行 `openspec validate build-habit-review-mvp --type change --strict`，并执行单元与端到端测试。
