## 用户故事

- **US-1**：作为个人用户，我想用邮箱和密码进入自己的数据空间，以便两个浏览器能够识别为同一个账号。
- **US-2**：作为已登录用户，我想让习惯和完成记录保存到本机 Postgres，以便退出、刷新或换浏览器后仍能读取同一份数据。
- **US-3**：作为已登录用户，我想继续使用创建、编辑、归档、打卡、周报、洞察和示例数据，以便更换持久化方式不会破坏现有使用闭环。
- **US-4**：作为数据所有者，我想继续导出和导入完整 JSON 备份，以便数据仍可读、可恢复且不会因失败导入被部分覆盖。
- **US-5**：作为账号数据所有者，我想让其他账号无法读取或修改我的数据，以便本地多账号验证具备真实的数据隔离。
- **US-6**：作为用户，我想在本地后端或鉴权失败时看到明确状态，以便不会误以为未持久化的数据已经保存。

## 验收准则（AC）

### AC-1 · 使用邮箱密码创建账号

- **Given** 用户未登录，且本地 Supabase 允许邮箱注册
- **When** 用户提交格式有效的邮箱和满足本地 Auth 规则的密码
- **Then** 系统创建账号并进入该账号的数据空间，不要求邮箱确认，也不自动载入旧 `xunji.store.v1`
- **验证方式**: `手动 UAT-01`

### AC-2 · 登录失败不得进入业务数据

- **Given** 用户未登录
- **When** 用户提交错误邮箱或密码
- **Then** 系统显示可读的登录失败状态，不进入今天、本周、洞察或管理页面，也不展示任何账号的 Habit 或 Completion
- **验证方式**: `手动 UAT-02`

### AC-3 · 恢复会话与退出

- **Given** 用户已成功登录并拥有有效会话
- **When** 用户刷新页面，随后执行退出
- **Then** 刷新后系统恢复同一账号会话和数据；退出后清除当前界面的账号数据并返回登录入口，但不删除 Postgres 数据
- **验证方式**: `手动 UAT-03`

### AC-4 · Chrome 写入后 Edge 读取

- **Given** Chrome 与 Edge 位于同一台电脑，且用户可在两者登录同一账号
- **When** 用户在 Chrome 创建一项习惯并记录当天完成量，再在 Edge 登录或刷新同一账号
- **Then** Edge 显示相同的 Habit、Completion 和由它们计算的今日进度
- **验证方式**: `手动 UAT-04`

### AC-5 · Edge 更新后 Chrome 读取最新值

- **Given** Chrome 与 Edge 已登录同一账号并读取到相同数据
- **When** 用户在 Edge 修改一条允许修改的完成记录，再在 Chrome 刷新或重新进入页面
- **Then** Chrome 显示 Edge 已持久化的最新值，且不存在同一账号、同一习惯、同一日期的重复 Completion
- **验证方式**: `手动 UAT-05`

### AC-6 · 退出再登录后数据仍存在

- **Given** 用户已经创建习惯、打卡并确认保存成功
- **When** 用户退出账号后使用相同账号重新登录
- **Then** 系统从 Postgres 恢复相同的习惯、归档状态和完成记录
- **验证方式**: `手动 UAT-06`

### AC-7 · 不同账号相互隔离

- **Given** 账号 A 已有习惯和完成记录，账号 B 已登录同一套本地后端
- **When** 账号 B 正常读取数据，或使用账号 B 的会话请求账号 A 的已知记录
- **Then** 账号 B 不能读取、修改或删除账号 A 的任何 Habit 或 Completion
- **验证方式**: `手动 UAT-07 + pnpm exec supabase test db`

### AC-8 · 未登录请求无业务数据权限

- **Given** 浏览器没有有效账号会话
- **When** 浏览器请求 Habit 或 Completion 数据
- **Then** 请求不能返回或修改任何业务数据，页面保持在登录入口
- **验证方式**: `pnpm exec supabase test db`

### AC-9 · 既有习惯与统计规则不得退化

- **Given** 已登录账号包含有效、已归档和不同目标次数的习惯及历史完成记录
- **When** 用户创建、编辑、归档、记录或修正最近七天，并查看本周和洞察
- **Then** 目标锁定、有效日期、最近七天、周报、洞察和共现结果继续符合既有 OpenSpec，不因数据源变化而改变
- **验证方式**: `pnpm test:run`

### AC-10 · 示例数据属于当前账号

- **Given** 已登录账号当前没有 Habit 或 Completion
- **When** 用户选择载入示例
- **Then** 示例习惯和完成记录只写入当前账号，并在刷新、退出再登录及另一浏览器登录后仍可读取
- **验证方式**: `手动 UAT-08`

### AC-11 · 导出当前账号的完整备份

- **Given** 当前账号包含活跃习惯、已归档习惯和完成记录
- **When** 用户导出 JSON
- **Then** 导出文件保持 Store v1 格式，包含当前账号全部 Habit 与 Completion，且不包含其他账号数据
- **验证方式**: `手动 UAT-09`

### AC-12 · 有效导入原子替换当前账号数据

- **Given** 用户选择一个通过 Store v1 完整校验的 JSON 文件，并已看到将替换的习惯数和完成记录数
- **When** 用户明确确认导入
- **Then** 系统以一次原子操作完整替换当前账号的数据；另一账号不受影响，刷新后展示新数据
- **验证方式**: `手动 UAT-10`

### AC-13 · 无效或取消导入不改变数据

- **Given** 当前账号已有数据
- **When** 用户取消导入，或导入文件存在无效版本、日期、引用、数值、重复记录或归档区间
- **Then** 系统不新增、删除或修改任何当前账号数据，并显示取消结果或可读错误
- **验证方式**: `pnpm test:run`

### AC-14 · 旧 localStorage 保持原样且不参与账号数据

- **Given** 浏览器已有 `xunji.store.v1`，其内容与当前账号 Postgres 数据不同
- **When** 用户注册、登录、读取、写入或退出
- **Then** 系统不自动导入、不覆盖、不删除该键，也不把它显示为当前账号的权威数据
- **验证方式**: `手动 UAT-11`

### AC-15 · 后端失败不得伪造成功或本地回退

- **Given** 用户界面已显示一份最后确认保存成功的数据
- **When** 本地 Auth、Data API 或 Postgres 不可用时，用户尝试登录、读取或写入
- **Then** 系统显示对应失败状态；写入不显示成功，界面不采用未确认候选值，也不回退到 localStorage 保存 Habit 或 Completion
- **验证方式**: `手动 UAT-12`

### AC-16 · 离线只保证应用壳可打开

- **Given** 用户曾成功加载 PWA 应用壳，但当前本地后端不可访问
- **When** 用户离线打开应用
- **Then** 应用壳可以显示，但账号数据读写明确标为不可用；系统不得宣称离线业务操作已保存
- **验证方式**: `手动 UAT-13`

### AC-17 · 账号与后端状态可访问

- **Given** 用户使用键盘或辅助技术访问注册、登录、退出、加载、成功和错误状态
- **When** 用户完成相应操作或后端返回结果
- **Then** 所有控件均有可读名称、可见焦点和至少 44×44 CSS 像素触控目标；结果同时以可见文本和辅助技术可读取状态表达，不只依赖颜色
- **验证方式**: `pnpm test:e2e`

### AC-18 · 同账号数据读取性能

- **Given** 本机 Supabase 正常运行，用户会话已有效，当前账号包含 10 个习惯和 3,650 条完成记录
- **When** 在同一台验证电脑上连续刷新并测量 20 次，从开始读取账号数据到今天页习惯列表和摘要可用
- **Then** 至少 19 次耗时不超过 1 秒，且每次都读取完整数据而不是被 Data API 单页上限截断
- **验证方式**: `手动 UAT-PERF-01`

### AC-19 · 客户端不得包含高权限密钥

- **Given** 应用完成本地构建
- **When** 检查 `src/`、构建产物和提交差异
- **Then** 客户端不包含 `service_role`、数据库密码、签名密钥或其他可绕过 RLS 的凭据
- **验证方式**: `rg -n "service_role|SUPABASE_SERVICE_ROLE|postgresql://|signing_keys" src dist`

## 范围切分

### v1（本次必做）

- 本地邮箱密码注册、登录、会话恢复和退出；不要求邮箱确认。
- Habit、Completion 进入当前账号的数据空间，并通过服务端权限隔离。
- Chrome 与 Edge 的同账号双向读写验证，以及第二账号隔离验证。
- Postgres 成为业务数据唯一真相源；旧 `xunji.store.v1` 保持原样但不参与账号数据。
- 现有习惯生命周期、打卡、周报、洞察、示例数据和 JSON 导入导出全部保留。
- 有效导入原子替换当前账号数据；取消或失败不改变数据。
- 后端不可用、未登录和离线状态不伪造成功、不本地回退。
- 登录及后端状态继承现有 UI、响应式和可访问性基线。
- 完成 10 个习惯、3,650 条完成记录的 20 次本地读取性能验证。

### v2（下一轮考虑，不本次）

- 为旧 `xunji.store.v1` 提供显式预览、确认和迁移工具。
- Realtime 推送、并发冲突检测或自动合并。
- 跨设备、局域网或托管环境访问。
- 邮箱确认、找回密码、OAuth 和账号资料管理。
- 生产部署、监控、备份和灾难恢复。

### out（永远不做）

- 不把 Supabase 本地开发栈直接暴露到公网或当作生产环境。
- 不在浏览器客户端保存或打包 `service_role`、数据库密码或签名密钥。
- 不以仅前端过滤替代数据库 RLS，也不在后端失败时静默写回业务 localStorage。
- 不让账号之间共享、浏览或协作编辑彼此的个人习惯数据。
- 不根据执行记录推断用户未完成原因或生成 AI 评价。

## 非功能性需求

- **性能**: 在 10 个习惯、3,650 条完成记录和有效会话条件下，本机连续测量 20 次，至少 19 次在 1 秒内完成完整账号数据读取并使今天页习惯列表与摘要可用；分页不得遗漏记录。
- **可访问性**: 新增账号和后端状态继承现有 UI-SPEC：键盘可达、可见焦点、至少 44×44 CSS 像素触控目标、状态不只依赖颜色，并通过可见文本与辅助技术可读状态表达结果。
- **安全**: Habit 与 Completion 的读取和写入必须由账号级 RLS 保护；未登录角色无业务数据权限；客户端不得包含可绕过 RLS 的高权限凭据；不同账号隔离必须有数据库测试证据。
- **兼容性**: 本次必须在同一台 Windows 电脑的 Chrome 与 Edge 验证；现有 320、390、768、1024、1440 CSS 像素响应式边界不得回归。
- **数据完整性**: 业务写入只有在 Postgres 确认成功后才更新为已保存状态；有效导入必须原子替换，失败或取消必须保持原数据；Store v1 领域校验继续生效。
- **隐私**: 用户业务数据仅进入本机 Supabase/Postgres，不接入公网第三方服务，不记录真实密码、token 或个人习惯数据到仓库和测试日志。
- **可观测性**: 不新增外部埋点；登录、会话恢复、读取、写入和导入失败必须在 UI 显示可读类别，测试报告记录失败阶段与耗时，但不得输出密钥或真实个人数据。
- **离线边界**: PWA 应用壳可缓存打开，但本次不提供离线业务读写、队列或同步承诺；本地后端不可达时必须明确阻断写入。

## 依赖与假设

- 依赖项目内 `@supabase/supabase-js`、Supabase CLI、`supabase/config.toml` 和可运行的 Docker 兼容环境；当前依赖与配置已存在，但业务接入尚未实现。— 来源：`@package.json:16-35`、`@supabase/config.toml`
- 假设本轮只在同一台电脑上运行前端和本地 Supabase；不假设局域网或公网可达。
- 假设验证账号使用非真实测试邮箱和测试数据；真实密码、token 和个人数据不得写入仓库。
- `supabase/config.toml` 的 `site_url`、数据库约束、原子导入边界、分页方式和错误分类由 DESIGN 确认，不在 REQUIREMENT 预设实现。
- schema migration 的生成、执行和回滚属于后续 DESIGN / TASK / DEV；执行任何 migration 前仍须按项目红线取得人工确认。
- 当前 OpenSpec 中“无账号、无后端、不同浏览器独立、离线可写业务数据”的旧边界将由本 change 的需求覆盖；其他习惯、统计、UI 和数据校验规则继续有效。
